# T0.8 — Docker build exposure (report only)

> **Superseded by T0.9.** The human chose option 1 (`--network=none`). See [`build-isolation.md`](build-isolation.md). The table below describes the M0 behaviour before that fix.

**No build-network change was made.** Ask before altering how `docker build` runs.

## How build runs today

Source: `apps/builder/src/docker-build.ts`

| Aspect | Current behavior |
|--------|------------------|
| Invocation | `execFile("docker", ["build", "-t", imageRef, contextDir])` — no shell |
| Network mode | **Default** builder network (no `--network` flag) |
| User | Build runs as daemon default; Dockerfile `USER` applies only after that instruction |
| Build args | None passed |
| Host mounts | None into the build; context is a host directory path |
| Daemon | Host Docker socket (`dockerode` / CLI on the builder machine) |

Uploaded Dockerfiles therefore execute `RUN` steps with the same outbound reachability as any other local `docker build`.

## Probe from a `RUN` step

Probe image: Alpine, `nc -z` against targets via the default bridge gateway (`172.17.0.1` on this agent). Control-plane port was listening on the host during the probe; Postgres and Mailpit were published via `docker compose`.

| Target | Result |
|--------|--------|
| Control plane `:4000` | **PASS** (reachable) |
| Postgres `:5432` | **PASS** (reachable) |
| Mailpit `:8025` | **PASS** (reachable) |
| Host gateway IP | **PASS** (reachable; other host ports on that IP answered; `:22` closed) |
| Internet (`1.1.1.1:443`) | **PASS** (reachable) |

`host.docker.internal` was absent in this Linux VM probe; host reachability was via `172.17.0.1`.

Interpretation: a malicious `Dockerfile` `RUN` can talk to local platform services and the public internet during build. Runtime app networks (`Internal: true`) are a separate, stricter boundary.

## Options (tradeoffs) — do not apply without asking

1. **`--network=none`** — Blocks all `RUN` network use. Breaks `apk`/`apt`/`npm install` in Dockerfiles unless deps are vendored. Strongest isolation; highest app-author friction.
2. **Allowlisted build proxy / BuildKit** — Forward only approved registries. More ops complexity; still need to keep control-plane/Postgres off the allowlist.
3. **Isolated buildkitd / separate Docker context** — Builds never see the host bridge. Cost and operational overhead; best long-term for multi-tenant.
4. **Keep default for M0; harden in T2.x** — Accepts build-time exposure until egress/build hardening lands. Matches current spike scope; document the risk (this report).

Recommended next step when ready: ask before choosing; prefer (1) for adversarial samples and (2) or (3) for friend-facing publish.
